### 现状与关键约束

- `compose.yaml` 已有 PostgreSQL、API、健康检查及命名数据卷，但 API 只等待数据库健康，没有自动建表与导入。
- `docker/postgres/init/01-databases.sql` 仅在空卷时创建账号和数据库；修改 `.env` 不会更改已有卷内账号密码。
- `.env.example` 要求应用密码在三个 URL 中重复填写，容器路线又单独依赖 `CASETRACE_CONTAINER_DATABASE_URL`。
- `storage/schema.py` 已支持重复建表；`storage/snapshot.py` 已有事务导入、元数据和内容摘要检查，优先复用。
- 现有 `import_snapshot()` 只对相同快照返回 `no_op`，不同快照会拒绝；`verify_snapshot()` 会比较源文件。不能在每次启动时无条件执行现有 `import/verify`，否则未来上传数据会被误判为失败。
- `/health` 只表示 HTTP 进程存活。01 的成功条件还须包含数据准备完成，不能仅以该接口判定初始化成功。

### 建议收敛的实现方案

1. 提供 `scripts/start-demo.sh` 和 `scripts/start-demo.ps1` 两个薄入口。宿主只需 Docker/Compose 与对应 shell，不新增 Python/uv 前提。首次和再次启动使用同一入口；目标命令分别为 `bash scripts/start-demo.sh` 与 `./scripts/start-demo.ps1`。
2. 入口负责 Docker/Compose/daemon 检查、首次配置、调用 Compose 及成功/失败提示。数据判断和初始化放在容器内 Python 中共享，避免 Bash 与 PowerShell 各实现一套数据库逻辑。
3. `.env` 不存在时生成两份不同的随机数据库密码并写入配置，模型密钥默认留空。已有文件保留原值、密钥和自定义端口；缺项或旧配置矛盾时给出具体修复提示，不静默重置密码。已有卷但配置丢失时提示恢复凭据，不自动删卷重建。
4. 容器数据库连接由单一应用密码及固定容器主机/库名构造，正确处理密码编码；取消容器对重复填写 URL 的要求。保留宿主开发与测试的显式 URL 入口，说明旧配置迁移和优先级，不在本阶段扩展成通用配置框架。
5. Compose 增加一次性数据准备服务，复用 API 镜像；依赖 PostgreSQL 健康，API 依赖数据准备成功。启动入口显式保证每次运行都会执行准备检查，不能依赖之前已退出容器的成功状态。准备服务失败时入口返回非零，不输出成功地址；已有运行中的服务也不能掩盖本次失败。
6. 保留现有命名卷及项目身份，正常停止使用 `docker compose stop` 或不带 `-v` 的 `down`。入口不自动换端口、删除数据或执行密码轮换。

以上方案已随本任务确认实施。依赖瘦身不纳入 01 必做范围；保留现有锁文件与构建路径，避免分散启动链路工作。

### 数据准备的行为契约

| 数据库状态 | 预期行为 |
|---|---|
| 尚无应用结构 | 建表，再按空实例路径处理 |
| 结构兼容、无快照元数据且业务表为空 | 在事务内导入随镜像提供的示例，核对成功后才继续启动 |
| 有有效快照且内容摘要一致 | 读取并校验当前内容，保留快照身份、导入时间及所有数据；不与示例文件比较，不重新导入 |
| 无元数据但已有业务数据 | 明确报错并保留原库，不能把它视为空实例 |
| 结构版本不兼容、摘要损坏或数据库连接失败 | 明确失败，保留数据，给出对应诊断步骤；不退回文件样例假装可用 |

复用现有元数据锁和事务边界，保证检查后写入不会竞争；不新增独立的“初始化完成”文件作为事实来源。首次导入中断后重试不能留下半份样例。

任务 03 继续负责上传快照身份、替换和查询支持；01 不提前解除回答核心的 dev-v3 限制。01 的准备逻辑必须不依赖固定样例身份，为 03 留出兼容边界。03 完成后联合验证“上传 → 重启 → 仍可查询上传内容”，该项在此之前保留为待验收。
