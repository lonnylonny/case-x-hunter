## 待决定与边界

采用独立 `POST /search`，复用当前 `check-only` 背后的 `prepare_answer_run` 与 `build_evidence_context`；生成继续走现有 `POST /answer` 回答核心。接口只做适配，不复制回答逻辑。`GET /model-status` 仅报告配置布尔值，不构造客户端或验证凭据，不返回密钥。

无密钥时展示候选与证据原文，明确未生成调查参考；不凭命中、排名或分数判断证据充分。支持不足与空命中分开：前者可能仍有检索候选，模型对支持程度的判断须接受语义审阅。

本阶段不更换 R3、模型或提示词，不重标既有 qrels。示例及人工验收意见不自动成为新 Ground Truth，也不升级源 Case 的 draft 状态。

1. Agent 整理至少三个示例、实际候选、历史原文与语义验收草稿，形成[工程师审阅表](../reviews/02-search.md)。本步已完成。
2. 用户确认示例适用性、相关性边界及缺口表达。Agent 起草意见，用户负责最终工程判断。本步已完成整体展示确认，不新增正式标签。
3. Agent 完成独立检索入口、模型配置状态提示及搜索页交互，补充 API 回归和固定回放验证，执行浏览器关键流程检查。
4. 用户审阅实际展示的参考价值和证据支持；Agent 修正、记录结果与限制。02 的关键情境在本阶段验证，综合约 10–15 题展示检查留到 05。

用户无需参与接口设计或测试实现；重点审阅案例是否值得参考、证据支持到哪一步，以及当前缺口是否有调查意义。
