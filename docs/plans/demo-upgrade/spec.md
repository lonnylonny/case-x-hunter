# Case-X-Hunter 求职展示升级规范（草案）

状态：需求范围及 01、02 已确认；03 于 2026-10-23 完成多 Detail／多调查项目上传、自动验证及双向审查，用户浏览器实操确认通过。04–05 尚未实施。实际证据及限制见各任务。

## 问题与目标

面向初级 AI 应用开发和 FDE 求职，改善现有半导体历史案例调查工具的启动、交互与资料维护。以本人约五分钟演示为首要场景，兼顾招聘方克隆后体验。20 小时是投入上限参考，不是必须填满的工期或承诺。

沿用 Python、FastAPI、PostgreSQL、Docker、原生 HTML/CSS/JavaScript 与现有检索回答核心。不转型为通用知识库，不引入新前端框架，不为展示堆叠技术。

## 权威来源与现状

使用仓库根目录 CONTEXT.md 的术语，遵守 docs/design/behavior-contracts.md 与 docs/data/ 的结构和业务规则。本草案不自动覆盖现行约定；实施时须明确修订与本次确认需求冲突的固定快照限制，保留其他约束。

制定本规范时已有 BM25/Embedding/Hybrid/Rerank 实验，正式回答使用 R3；已有引用定位校验、回答记录、PostgreSQL 原子导入、FastAPI 与网页。当时导入不支持任意数据替换，回答绑定 dev-v3；03 新增独立登记的上传快照与整体替换，保留历史文件路线的复现边界。Case/Detail/Evidence 关系与产品、工序等主数据约束仍有效。SQL 是结构化存储，不是自然语言转 SQL 功能。

## 用户故事与行为要求

1. 作为演示者，我希望在已准备 Docker 和 Compose 的环境中用少数步骤启动服务，避免逐条初始化数据库。
2. 作为首次体验者，我希望自动获得可公开使用的示例案例和至少三个示例问题，无需先准备资料。
3. 作为无模型密钥的体验者，我希望检索历史 Case 并查看证据，页面不把检索结果冒充模型回答。
4. 作为配置密钥的使用者，我希望得到有来源的调查参考，包括历史原因、检查和措施，以及当前信息缺口。
5. 作为使用者，我希望资料无法支持回答时明确提示不足，不把历史根因表述为当前 Incident 的最终根因。
6. 作为资料维护者，我希望下载唯一固定 CSV 模板，在网页上传后更新当前数据集。
7. 作为资料维护者，我使用唯一 CSV 模板，以 record_type 区分 Case、Detail、Evidence，通过 case_id 保留每案多个 Detail 和多个调查项目，并复用现有合法主数据值（2026-10-23 用户修订确认，覆盖旧一行一案限制）。
8. 作为资料维护者，我希望缺列、空必填项、非法引用或其他业务校验失败时看到具体问题；能定位时标明行列，不进行部分导入。
9. 作为使用者，我希望新数据成功导入后整体替换当前数据集；失败时旧数据仍可查询，重启后成功导入的数据仍存在。
10. 作为使用者，我希望看到当前数据集名称、案例数量与更新时间，清楚查询依据是什么。
11. 作为演示者，我希望最多两个页面：搜索页与设置页；看到清晰的加载、成功、空命中及失败状态。
12. 作为使用者，我希望设置页提供上传、数据状态、必要模型参数与高级 Top K；密钥保存在本机 .env，网页仅显示是否配置。
13. 作为 Windows 用户，我希望在 Docker Desktop 已准备好的前提下，通过 PowerShell 完成文档规定的启动；不要求安装包或双击启动。
14. 作为求职者，我希望保留可解释的实验结果和失败案例；新上传数据不继承旧数据集的评估指标。

## 已确认的实现边界

- 保留半导体领域、现有业务模型及检索相关性定义；不把同产品或同批背景直接当作 Relevant。
- 唯一 CSV 格式、单一当前数据集、整体替换，不做增量合并或逐行编辑。模板不能为满足模型而编造未知业务字段。
- 当前运行数据与原始样例、Development、Locked Test 和实验结果分离；上传不得覆盖后者。
- CLI/API 继续共用检索、上下文、生成和引用校验核心。复用现有事务能力，不能直接假设现有 import 已支持 replace。
- 保留数据来源、关系、原文和 review 状态。数据可用时点必须有依据，不能将 detection_time 当成结案时间。
- 只保证现有 DeepSeek 调用链路；不承诺任意 OpenAI 兼容服务。网页不接收或保存密钥，不返回密钥明文。
- 未配置密钥仍可使用检索。模型失败、格式失败、引用失败不得包装为成功；空命中不调用模型。
- 正常停止或再次启动不得覆盖已导入数据；初始示例只用于尚未初始化的实例。
- Docker Compose 是统一主启动路线；保留 Python 开发入口，不另建无 Docker Windows 产品路线。

## 测试边界提案（待审阅）

优先通过既有 FastAPI 边界验证用户可见行为，用真实 PostgreSQL 集成测试验证替换事务和重启持久性。模型响应采用既有固定回放；真实模型调用与人工回答质量审阅独立记录。无需对所有内部函数编写镜像测试。

1. API/页面：无密钥检索、带引用回答、空命中、资料不足与显式错误；Top K 边界和配置状态。
2. 导入：合法模板、缺列、空字段、非法主数据值、重复标识等有意义失败；任何失败均不破坏旧数据；替换后不混入旧案例。
3. 持久性：成功导入后重启，当前状态和检索内容一致；重复启动不重置为示例。
4. UI：搜索和设置的完整路径，上传反馈、引用可追溯、加载和失败提示。
5. 启动：干净环境首次启动、再次启动、保留数据的停止再启动；Windows 需真实环境验证，否则明确标为未实测。
6. 质量：复用现有证据，补充小型约 10–15 题的展示检查，含无词项命中、常见词重合但缺乏支持证据、正常及易混淆问题。期望结果需人工确认；不用 Locked Test 调参，不因软件测试通过就宣称回答可靠。

## 最终验收

- [ ] 按 README 从满足前提的干净环境启动，自动准备示例数据。
- [ ] 无密钥可检索案例和证据；有密钥可生成可追溯回答。
- [ ] 无支持证据时说明不足；不承诺完全消除幻觉。
- [ ] 有效上传后能查询新数据，无效上传后旧数据仍可查询。
- [ ] 重启后数据保留，页面状态与实际数据一致。
- [ ] 搜索与设置不超过两个页面，不要求用户理解内部实验快照编号。
- [ ] 提供 Windows PowerShell 操作步骤，实测情况如实记录。
- [ ] 展示材料明确合成数据、规模与质量限制，保留既有实验边界。
