# 04：新增完整案例

**交付行为：** 使用者通过资料库创建完整案例，登记首次来源，填写多条明细和调查证据，保存后立即可浏览及搜索。

**Blocked by：** [03 编辑与修订记录](03-case-editing.md)。

**Status：** 2026-11-06 已实现；API、真实 PostgreSQL 与 HTTP 夹具浏览器通过；真实实例浏览器闭环待 06。

规范：[完整规格](../spec.md)。定位与执行次序见 [计划](../plan.md)。

## 验收标准

- [x] 资料库提供新增入口，复用已交付的分区表单，支持多个 Detail 和多个 Case 级 Evidence。
- [x] 新 Case、Detail、Evidence 编号自动产生且唯一；批号保持字符串及前导零，不复制旧案的主键。
- [x] 新案默认不入组，不自动创造分组；主数据只选用当前合法值，客户等背景由产品显示。
- [x] 新记录首次登记来源，真实与合成资料的说明清楚；同报告基本信息可复用，具体位置对应记录，不伪造 CSV 行号。
- [x] 至少一条明细与一项证据、结案声明、异常工序及其他必填项经现有规则检查；不保存半成品或升级人工审阅状态。
- [x] 比当前资料更晚的内容可通过同时更新日期及依据纳入，未满足时点或声明条件则拒绝整次保存。
- [x] 用至少 2 条明细、3 项证据的新案完成保存，详情保持逐条对应，来源和初次保存记录准确。
- [x] 超限、重复/非法引用、跨案批号矛盾、缺少来源、过期快照或写入失败均不部分入库，输入保留。
- [x] 成功新增后列表总数、详情、资料身份和新搜索一致；取消不改变现有资料。
- [x] 重启保留新案例及来源/修订记录，文件样例与评估数据不变；新增不需要调用模型。

## 验证与交接

API 和真实数据库验证多子记录创建、无效输入、跨案关系、冲突、原子性和重启；浏览器验证从新增到搜索的完整路径。提供一个合法无分组案例夹具供 05/06 验证最后一案删除及空库重建，不要求真实用户数据作为测试材料。

零案状态的“新增后恢复搜索”闭环由 06 结合 05 验收；本包不依赖 05 才能完成普通新增流程。

## 细化执行计划（2026-11-06，待确认）

执行总入口：[剩余工作计划](../remaining-work.md)。本节固定新增行为和验证边界，不改变原规格。

### 1. 公开写入契约

- 增加 `POST /cases`，JSON 沿用整案编辑的字段结构：`expected_snapshot_id`、`case`、`details`、`evidences`、`closure_status`、可选 `availability`。新增不接受客户端 Case/Detail/Evidence ID，也不接受分组、客户归属或审阅状态覆盖。
- 每条新记录必须登记 `origin`；至少 1 Detail、1 Evidence。复用 5 MiB 输入上限、严格字段、500 案/10000 业务记录边界及既有领域规则。
- 成功 HTTP 201、`status=created`，返回新 `case_id`、`dataset` 和带快照/来源/初次修订的 `detail`，前端据此进入新案详情。422 返回可定位错误；409 表示快照冲突；413 超限；503 表示存储不可用或结果需核对。错误不得泄漏底层连接信息。
- 重复提交相同旧身份最多成功一次；响应丢失后不自动重试创建，保留表单并要求核对当前列表，避免生成第二案。

### 2. 候选、来源和原子写入

在现有编辑领域模块复用必要的字段/来源/时点/候选校验，保持新增与编辑的入口清楚；不通过先写占位案再编辑实现新增。系统在锁内读取当前快照、核对预期身份，生成唯一 ID，构造完整新案候选后一次写入。

新案默认不入组。来源为报告或明确人工合成；允许复用报告编号/名称，具体位置逐条填写，不伪造 CSV 元信息。建立当前来源及 `operation=create` 的一条初次修订，待人工审阅；不虚构编辑前历史。更新顺序、内容摘要和新运行身份，沿用原文件摘要表示来源沿革。

复用 `snapshot.py` 的事务、元数据锁及 `_replace_entities` 读回校验；实体、来源、修订和快照任一步失败全部回滚。已有案例/分组/主数据/设置保持原内容；跨案批号矛盾必须在完整候选集上拒绝。无需 schema 迁移。

### 3. 页面

资料库列表区和空库区提供“新增案例”，无需先打开旧案。将 `library-editor.js` 以显式新增/编辑模式复用，不依赖伪造 `currentCase`。读取同快照参考选项；新增默认一条明细与一项证据，可增删至所需条数；保存前允许临时不完整，提交时统一校验。

保留顶部 sticky 保存/取消栏、日期声明、未保存离开提示、来源分区、重复点击保护与迟到响应检查。错误保留输入并定位字段；409 禁止继续用旧身份写入；取消回列表。成功清理旧缓存，展示新案详情并刷新计数；清楚说明活动筛选可能不包含新案。搜索可查到新增内容，无需模型。

实际改动：

- `data/case_editing.py`：提取共享的完整候选校验 `_candidate_errors`；新增 `prepare_case_creation`（Case 自身由服务端生成 `C<uuid>` 编号，子记录生成 `D<uuid>`/`E<uuid>`；Case 与每条子记录强制首次来源；不接受客户端记录编号；新案默认不入组；写 `sources[case_id]` 的逐记录 `web_provenance.origins` 与 `operation=create` 初次修订）。
- `storage/snapshot.py`：新增 `create_case_snapshot`，锁内核对 `expected_snapshot_id`、构造完整候选、以 `create-<uuid>` 身份原子替换并读回。
- `api.py`：新增 `POST /cases`（201 created／409／422 可定位 errors／413／503），成功返回 `case_id`、`dataset` 与含来源和初次修订的 `detail`。
- 页面：资料库列表区新增“新增案例”入口；`library-editor.js` 增加显式 `create` 模式复用中文分区表单（不伪造 `currentCase`），默认一条明细与一项证据、来源区块默认展开；新增成功清理旧列表缓存并展示新案详情；`library.js` 详情来源区区分报告/合成/新建来源，修订区显示“新建案例”。
