**交付行为：** 使用者打开现有案例，修改案例及多条明细/证据，统一保存；原来源自动沿用，成功修改产生默认折叠的修订摘要，立即影响新搜索。

## 验收标准

- [x] 提供中文分区编辑，支持修改整案及添加/移除明细和证据，统一保存/取消；既有 ID 稳定，新增子记录 ID 唯一。
- [x] 主数据按名称与编号选择，产品对应客户/路线自动展示；不自动推断已确认工序，不静默移除不合法选择。
- [x] 内置合成案例与 CSV 上传案例都可编辑；已有来源默认保留，不要求每次重填或确认；新增子记录首次登记适用来源。
- [x] 原合成来源合法保留，修改后标记人工修订；原 CSV 行号只能说明原出处，不冒充修改后内容的原文证明。
- [x] 日期和依据默认沿用；需要改变时与本次保存同事务更新，并确认整份资料完整可用声明；不采用保存时间推导结案时间。
- [x] 针对完整候选集执行适用校验，非法字段、主数据、批号、confirmed 证据门槛及分组工序冲突定位明确；不套用合成采样 GR。
- [x] 修改导致组不合法则拒绝，不解散组、不改其他案例来凑合法结果。
- [ ] 实体、来源、顺序、修订记录和新快照摘要原子保存并读回验证；中途失败全部回滚，页面保留编辑输入。
- [x] 正常取消和无变化保存不产生虚假修订；有未保存内容时离开提示，普通保存不反复弹来源确认。
- [ ] 每次实际成功修改自动记录时间及变更字段/增删子记录摘要；默认折叠，可展开查看，刷新及重启保留，无历史不伪造历史。
- [x] 不采集编辑者姓名、不要求手写说明、不做全文对比/回滚；修订摘要不作为模型调查证据。
- [ ] 编辑提交预期快照身份；过期返回 409 并保留输入，不自动合并；CSV 以及已落地的恢复入口一并遵守冲突检查。
- [ ] CSV 或恢复整体替换后不残留原修订记录；兼容没有修订元数据的既有快照，不要求用户重新导入才能编辑。
- [x] 内置示例首次修改后作为用户维护运行资料，保存身份与来源沿革正确，不回落到固定 dev-v3 身份或继承旧评估结论。
- [x] 新搜索读取修改内容；进行中回答及其下载保持旧快照，来源显示清楚；取消、校验失败和冲突均不改变原库。
- [ ] 模型/检索设置及原始数据文件保持不变，正常重启不覆盖修改。

### 2. 公开接口与 ID 规则

计划新增 `PUT /case?case_id=...`，整案提交，不设计逐字段 PATCH。query 使用与 GET 相同的编号语义，不能改成路径参数或新收紧合法历史编号。

| JSON 字段 | 契约 |
|---|---|
| `expected_snapshot_id` | 必填非空；来自打开编辑时的快照，不在提交前偷偷换成最新身份 |
| `case` | 全量可写业务字段：异常、根因、措施、其他说明、已确认异常工序；不含可改写的 `case_id` |
| `details` / `evidences` | 本次保存后的完整子记录集合；既有记录带原 ID，新记录省略 ID；父 `case_id` 由服务端绑定。省略既有记录表示明确移除 |
| `closure_status` | 显式 confirmed/NDF 来源声明，原值预填，不能由根因文本推断 |
| 每条记录的 `origin`（可选） | 既有记录省略即保留来源；显式修改或新子记录使用下节的真实/合成来源结构。来源随记录提交，避免新记录尚无服务端 ID 时另造临时引用协议 |
| `availability`（可选） | 普通保存省略即沿用日期/依据；改变时提交完整 `known_at`、`basis` 及 `confirmed_complete=true`。声明覆盖完整资料，不能仅声明本案 |

请求嵌套模型拒绝额外字段，不接受客户端指定修订日志、保存时间、基线身份、摘要、审阅升级、文件路径、schema、主数据名称或组关系。日期沿用 YYYY-MM-DD 严格边界；批号保持文本，数量拒绝 bool/小数并受数据库 integer 上限约束。请求设置明确的体积边界（沿用 5 MiB），候选全集沿用 500 案、10000 条 Case/Detail/Evidence 限制；修订摘要不计入业务记录数。

既有 ID 必须属于目标案例且在提交中唯一，拒绝伪造、跨案挪用或修改 ID；新增 ID 由服务端生成并核对对应实体全集唯一，不复用刚删掉的 ID。保留所有未修改案例及子记录的源顺序，既有目标子记录保留原相对顺序，新记录按表单顺序追加；本包不提供拖动重排。工序/异常类型属于无序集合，单纯选项顺序变化不算内容修改。

成功返回 `status=saved`、新 `dataset` 与完整 `detail`（含新身份、正式子记录 ID、来源和修订）；无实际变化返回 `status=unchanged` 与原身份/详情，不更新保存时间。过期身份在锁内先于案例查找、候选业务校验及无变化判断返回 409 `snapshot_conflict`；当前身份无案例为 404，结构及业务校验为 422，超体积为 413，服务错误为安全的 503/500，不回显连接信息。

业务错误响应使用 `errors` 数组，至少含实体/记录定位、字段与中文原因；新记录用提交数组路径定位，组约束带 group_id 与规则号。复用 validator 的规则结论，不重写 CR；不要只返回一段无法定位的异常文本。Pydantic 结构错误仍走现有 422 安全处理。

### 3. 来源、修订和旧快照兼容

- 旧的 `sources[case_id]` 合成候选、CSV 报告/物理行号及 closure_status 原样读入；未显式改来源的保留记录自动沿用。不要求旧库先转换或重新导入，不调用合成候选核对来禁止合法人工改写。
- 计划在来源中增补 `web_provenance`，只存被人工改动的记录标记及新增/显式修改的逐记录来源，使用 `(record_type, record_id)` 定位；旧快照缺键即无网页维护。保留既有原出处作为沿革，不保存旧正文。移除子记录时同步移除其当前来源条目，修订摘要仅记录被移除的 ID。
- `origin` 区分报告与人工合成。报告需具体的编号、名称和记录位置；合成需明确的人工合成说明与可定位位置。同报告可复用编号/名称，新增记录仍需自己的位置。客户端不能伪造原 CSV 文件/行号；旧合成案例新增子记录也须首次登记来源，可预填合成类别但不能自动捏造出处。
- 已有记录修改不弹来源确认；确需换出处时展开可选来源编辑。合成案例修改后明确标记“合成示例的人工修订”；CSV 原行号明确为原始导入出处，不能继续显示成修订正文的逐字证明。新来源不能因存在 `records` 就被误判为 CSV 报告。
- 逐案摘要计划存 `payload.case_revisions[case_id]`，每次实际保存追加服务端 UTC 时间、操作类型 `edit`、变更字段路径及增删子记录 ID。日期/依据或来源变更也计入摘要；不存全文前后值、编辑者姓名或手写理由。没有历史时返回空列表并显示“暂无网页修订”，不把 `simulation_revision` 转成网页日志。
- 保存时实体、当前来源、摘要与顺序一并入内容摘要。只有用户可保存的内容真正变化才生成修订及运行 ID；先比较规范化候选，再追加时间/随机身份，避免每次保存都因技术字段不同而产生假修订。新增后又移除且未改变其他内容，也应为无变化。
- 原始合成/CSV 来源标记仍可作为沿革，首次维护后增加明确的人工维护状态；`dataset_info` 与资料库显示“用户维护资料”，不能因保留 baseline/import_format 就继续称未修改演示库。新运行 ID 独立，原文件哈希继续表示原文件，基线来源保留；不得冒用旧评估结论。
- CSV/恢复成功整体替换时使用新 payload，不携带旧 `case_revisions` 或人工修订标记；失败时原样保留。缺少这些新键的现有快照仍按当前摘要正常读回，不补写空键改变旧摘要；不预先升级摘要算法版本或建新表。

### 4. 一次保存的事务顺序

1. API 完成结构校验及体积限制；存储开启事务，沿用 schema 版本检查和 `snapshot_metadata` 的 EXCLUSIVE 锁。锁内读回一次当前快照并核对预期身份，禁止先锁外准备候选、再用过期内容覆盖。
2. 找到目标案例，在内存候选中只替换本案与其子记录，合并原来源和显式来源输入；组/成员、其他案例及主数据保持原值。分配新增子记录 ID，并建立提交路径到记录 ID 的错误定位映射。
3. 对**完整候选集**运行 `validate_relations`，再检查来源、`check_confirmed_evidence`、全部发现时间不晚于候选 known_at、规模限制。CR-04 同客户、跨案批号一致、工序/路线、CR-38 与 CR-51 不放宽。不得调用 `validate_generation` 或 `check_source_records` 强迫人工文本继续包含原合成候选；演示恢复/文件导入仍保留原检查。
4. 比较用户可变内容；无变化则不写实体、日志或身份。日期/依据改变也属于实际变化，须有整库声明；默认沿用时不反复要求声明，不用保存时间推算结案/可用日期。
5. 实际变化才生成新快照身份、待人工审阅状态和一条逐案修订，重建目标来源与全局顺序；复用 `_replace_entities` 的窄范围事务能力写入并读回摘要检查。该函数现有物理整批重写不等于授权修改其他案例，测试必须比较其他内容完全相同。
6. 读回成功后提交，再返回新身份与详情。任一写入或读回异常回滚到原实体、来源、顺序、摘要及日志，不能先提交再补修订。必要的新事务函数供 04/05 调用，不预先实现其业务分支。

CSV 的 metadata/API/storage 调用同步新增必填 `expected_snapshot_id`，锁内在解析/替换之前检查；页面上传、API 用例、真实库夹具、浏览器脚本和文档一起更新，不保留缺省即可覆盖的后门。恢复维持现有必填规则。三入口复用相同冲突异常及 409 映射；编辑/CSV/恢复的任意交错写入只有先成功者生效，后者不得覆盖。进程内按钮禁用不能代替数据库锁内检查。

### 5. 页面状态与回答边界

- 在现有详情增加“编辑”及默认折叠的修订区。表单中文分为历史结论、批次明细、Case 级调查证据、来源、资料可用日期；分组/主数据只读。既有来源默认折叠展示，普通保存不要求重新确认。
- 产品选择显示名称和编号，联动展示客户/产品族/路线；异常工序由用户明确选择，路线不自动代填。遇到无效旧选择保留可见错误，不静默删项。新增/移除子记录在本地生效，至少子记录数量仍由完整保存校验。
- 保存/取消统一作用整案；dirty 比较初始内容，只有确有未保存内容时离开才提示，包括返回列表、导航、刷新和关闭。确认放弃才清草稿，正常取消不写库。编辑期间停用同页上传/恢复等干扰写入。
- 保存中禁止重复提交。422 显示记录/字段错误并保留输入；409 保留草稿、停用旧身份保存，明确提示刷新核对，不自动换新身份、合并或重新提交。刷新会放弃草稿时须确认；刷新后重新打开编辑。
- 网络结果不明时保留草稿，提示可能已保存，先核对当前身份/详情；不自动重发，不声称数据库一定未变化。继续使用 02 的请求序号及身份校验，迟到的详情/参考/保存响应不能混入另一视图。
- 成功后采用响应的新身份清理旧缓存、展示当前详情及摘要；保留列表筛选，重新回列表读取；无变化保存沿用原身份。修订区默认折叠，刷新/重新连接后内容仍存在。桌面与窄屏可操作，多行文本使用安全 DOM 渲染。
- [回答准备](../../../../src/casetrace/answer/context.py)继续使用请求内已加载快照，新搜索读新资料；[回答运行及下载](../../../../src/casetrace/answer/cli.py)保留旧记录。原始文件/评估入口不随网页保存改变。
- 回答来源投影只加入说明“人工修订/原出处沿革”的必要标记及当前合法来源；修订时间、字段摘要、技术摘要和整份修订列表均不进入检索文本或模型证据。同步修正搜索页 `renderContextCase` 对 `source.records` 的分支，避免丢掉人工维护标记。用实际发送消息与旧下载回放验证，不能只测 UI 文案。

### 6. 实施顺序与验证矩阵

按可观察的整案行为推进：先打通已有合成案的最小修改/取消，再加入多子记录及来源、完整候选校验和修订；随后统一三种写入的冲突处理，最后验证浏览器及回答回放。每步补有意义的行为回归，不先完成全部 SQL 或通用表单。

| 场景 | 证据与通过条件 |
|---|---|
| 基本保存/旧库兼容 | 公开 HTTP 编辑内置与 CSV 两案；GET、保存、新详情形状一致；缺少修订元数据也能编辑；原 ID 不变、新 ID 唯一、其他案例/组/主数据不变 |
| 无变化/取消 | 原样保存、无序选项换序、临时新增再移除无新 ID/时间/日志；取消不发写请求；实际字段/来源/日期变化恰好一条摘要 |
