## 已确认范围

- 三个导航入口：搜索历史案例、案例资料库、设置；资料库采用列表、完整详情、分区编辑。
- 历史案例及明细、调查证据、来源可维护，主数据只读；完整保存并校验通过后立即影响新搜索。
- 项目 V1 指九案完整演示库，不是名为 dev-v1 的旧归档。首次空库初始化载入九案库；网页可明确确认后重新载入，正常重启保留当前资料。
- 单案例 CSV 仅用于说明上传格式，改名消除与完整演示资料的混淆。
- 编辑已有资料自动沿用原来源；新增资料首次登记来源；不反复确认来源、不记录编辑者姓名。
- 修订记录默认折叠，自动记录修改时间和变更字段/增删子记录摘要；不要求手写说明，不做全文版本对比和回滚。整体替换资料时一并替换修订记录。
- 删除前确认；完整候选集校验失败则拦截，不自动解散组。现行 CR-38 仍要求每组至少两个不同案例；案例可以不入组。
- 允许合法删除后为空库，无回收站。资料日期及依据默认沿用，必要时随保存一起更新并确认完整可用声明。

## 实施纪律与验证

每包包含用户操作、API、必要存储改动与测试，不另开横向“先做所有后端”任务。只为可验证的行为提取必要公共函数，复用冻结模型及现有依赖。03 的事务、来源和修订记录是同一次保存行为，不拆出通用审计平台。

公开 HTTP 是主要验证边界；真实 PostgreSQL 验证事务、冲突和重启，浏览器验证完整操作与布局，回答采用离线回放。测试库未配置就明确记录跳过，不宣称通过。无需调用付费模型，不改 Locked Test 标签，不用软件测试宣称回答质量提升。

每包完成后在包内记录改动、命令、验证结果、截图链接和限制。06 复用前面证据，仅补跨包流程及新发现的缺口；不重复跑无关评测。01–03 的实际证据与真实库缺口见包内记录；04–06 尚未实施，不预先勾选验收项。

现有 JSONB 元数据可承载新增来源标记与修订摘要，优先使用现有结构。若实施发现确实需要 schema/旧数据迁移，先提出具体迁移方案，按仓库规则另行确认；不得通过清空用户库绕过兼容性问题。

上一轮 demo-upgrade 的已完成记录保持历史原貌；其构建收尾与展示准备任务不因本轮生成工作包而自动完成。业务约定及使用文档的运行行为说明随对应实现更新，不把已批准但未实现的功能描述为现状。
