# 网页案例资料库升级规格

状态：2026-11-05 用户完成需求访谈并确认本规格所述范围及六包拆分；2026-11-06 01–06 全部实施完成，隔离真实实例闭环、真实 PostgreSQL 事务/并发/空库与仅更新 API 的部署均已执行，整体证据见 [验收记录](acceptance.md)。执行入口见 [计划](plan.md)。

## 问题陈述

使用者难以在网页直接看清当前运行资料，缺少浏览整库与维护单案的入口。单案例上传格式示例容易被误认为完整演示数据，上传后整体替换九案库，导致演示内容不足且没有便捷恢复入口。

## 解决方案

增加案例资料库，提供当前资料概览、筛选列表、完整详情及分区编辑。历史案例、明细、调查证据和来源可维护，主数据只读。沿用单一当前数据集，完整保存通过校验后立即影响新搜索。

使用项目 V1 的九案完整资料作为演示基线，提供明确确认后的恢复入口。修订记录自动产生、默认折叠。删除失败由现有业务校验说明原因并拦截，不放宽分组规则。

## 用户故事

1. 作为演示者，我希望首次初始化载入九案完整资料，以便直接展示历史案例调查。
2. 作为演示者，我希望上传格式示例与完整演示库名称清楚区分，以免误将单案例样例当成完整资料。
3. 作为演示者，我希望在网页确认后重新载入完整演示库，以便在试用上传或编辑后恢复演示。
4. 作为资料维护者，我希望正常刷新和重启保留当前数据，以免丢失已经保存的修改。
5. 作为使用者，我希望看见当前资料的名称、来源、数量和时间，以便理解搜索依据。
6. 作为使用者，我希望无需提交调查 Query 就能浏览全部案例，以便检查数据库内容。
7. 作为使用者，我希望按关键词、产品、客户、异常站点和发现阶段筛选，以便找到要查看的案例。
8. 作为使用者，我希望完整查看每案的结论、明细、证据、来源及分组，以便理解关系而非只看到摘要。
9. 作为资料维护者，我希望按中文分区表单编辑并统一保存，以便像编辑普通文档一样维护资料。
10. 作为资料维护者，我希望一案支持多条批次明细与多项调查证据，以便保留完整调查记录。
11. 作为资料维护者，我希望产品等主数据提供选项及对应背景，以便减少输入错误。
12. 作为资料维护者，我希望新增资料首次登记来源、编辑已有资料自动沿用来源，以免重复填写。
13. 作为使用者，我希望能展开自动生成的修订记录，以便知道何时改过哪些内容。
14. 作为资料维护者，我希望校验错误指向具体记录与字段，以便修正而不破坏原数据。
15. 作为资料维护者，我希望过期编辑页面不能覆盖别人或另一标签页的新保存，以免丢失修改。
16. 作为资料维护者，我希望必要时调整整份资料的完整可用日期和依据，以便纳入较晚的新资料。
17. 作为资料维护者，我希望删除前知道关联影响，以便明确确认实际删除。
18. 作为资料维护者，我希望破坏分组等约束的删除被拦住，以便保持数据合法。
19. 作为使用者，我希望空库显示清楚，并能新增、导入或恢复演示，以便继续使用。
20. 作为使用者，我希望新搜索使用保存后的资料，进行中的回答仍能完成，以便结果身份保持清楚。
21. 作为演示者，我希望资料维护不依赖模型密钥，以便离线验证基本功能。
22. 作为项目维护者，我希望运行资料的修改不影响原始示例、评估数据和实验记录，以便保持复现边界。

## 实现决策

### 1. 演示基线与整体替换

- V1 指项目第一版完成时的九案资料：9 Case、9 Detail、9 Evidence、1 Group、3 Membership、5 条已有示例 Query。此处的 V1 不是 dev-v1 旧归档。
- 当前初始化本来已指向这份资料；复用已有源，不重写九案内容、不凭空扩充或重新生成。
- 首次“空库”指没有已登记运行快照。用户主动删到零案但仍有快照，不得在重启时被自动回填。
- 网页提供“载入完整演示数据”，显示当前资料将被整体替换并要求明确确认。取消不写库；替换失败保留原资料及修订记录。
- 恢复保留完整案例、子记录、分组、来源、原有日期及可用性依据，不通过不支持分组的 CSV 模板转换，以免遗漏信息。
- 每次明确恢复使用独立运行快照身份，保留演示基线身份作来源，避免重复固定 ID 导致过期页面误判为未变化。原始合成数据检查继续执行。
- 复用当前主数据，恢复前验证与演示基线兼容，不静默替换主数据。主数据不兼容时明确失败。
- 恢复后既有示例问题入口可正常使用；维护后的数据不继续冒充未改动的演示基线，也不继承旧质量结论。
- 单案例 CSV 仍用于说明多 Detail/多 Evidence 上传格式，入口明确标为“上传格式示例”；不新增完整演示库 CSV 导出要求。
- CSV 上传继续整体替换，成功后清除被替换资料的修订记录；设置参数不随数据替换重置。

### 2. 浏览与页面结构

- 主导航为搜索历史案例、案例资料库、设置。详情和编辑是资料库内部视图，不限制必须采用独立 URL 或弹窗。
- 概览显示名称、来源类型、案例/明细/证据数量、更新时间、完整可用日期及审阅状态；快照 ID、摘要等技术信息放在展开区域。
- 列表一案一行，显示编号、异常摘要、产品/客户、异常站点、发现日期范围、子记录数量；长文本在详情完整呈现。
- 支持关键词、产品、客户、异常站点、发现阶段筛选，清空筛选和分页。关键词覆盖编号、异常描述、历史根因、生产批及客户批；浏览不调用模型。
- 同时指定产品/客户/发现阶段时，同一条明细须满足明细条件，不能把不同明细拼成匹配。总案数与筛选结果数区分。
- 详情保持每条产品、批号、时间、处置的对应关系；Evidence 属于 Case，不强行绑定某条 Detail。
- 显示所属组与关联理由，主数据只读可查询；不提供分组或主数据编辑器。
- 加载中、服务错误、空库、筛选无结果分别表达。动态文本按文本呈现，保留现有安全渲染方式。

### 3. 新增与保存

- 编辑整案，支持增删明细和证据；统一保存/取消，不自动保存，不做服务端未发布草稿。
- 主数据显示名称和编号，产品关联的客户/产品族/路线自动展示；不得推断已确认异常工序。非法既有选择要提示，不静默删掉。
- 新 ID 由系统产生且在对应实体中唯一，既有 ID 保持稳定；批号按文本处理，保留前导零。
- 仅校验通过的完整案例可入库。新增子记录同样需要合法字段、来源及关系，不能先保存缺必填事实的半成品。
- 整体校验包括适用 CR、跨案批号一致性、主数据适配、结案证据门槛和组关系。用户维护资料不施加合成采样 GR；原合成入口保留原有检查。
- 错误尽量定位到案例、子记录及字段；不以通用失败信息掩盖可解释的业务错误。
- 保存失败保留输入，取消不写入；离开有未保存修改的页面才提示。
- 保存成功供新请求立即使用；资料仍为待人工审阅，保存不等于语义支持已确认。
- 先沿用现有 500 案、10000 条案例/明细/证据记录的规模边界；不把修订摘要计作 CSV 业务记录，不设置未经测量的性能承诺。

### 4. 来源与折叠修订记录

- 新增资料首次登记来源。真实资料沿用报告编号、名称、具体位置的现行要求；合成资料明确注明人工合成及可定位说明，不虚构真实报告。
- 编辑已有记录自动保留原出处，不每次重填或弹出来源确认；确实换出处时允许显式修改。
- 同一报告的编号和名称可复用，具体记录位置保持对应；新增记录不得伪造原 CSV 文件名或行号。
- 原内置合成来源继续有效，不强迫把旧合成记录转换为虚构报告。修改后标为合成示例的人工修订。
- 每次真正改变内容并成功保存，自动追加逐案修订记录：时间、操作类型、变更字段及增删子记录摘要。无变化保存、失败保存和取消不产生虚假修订。
- 修订区域默认折叠，点击展开按时间查看；无历史时明确表示暂无网页修订，不推造导入前历史。
- 不采集编辑者姓名，不要求手写说明，不保存全文版本对比，不做回滚。
- 修订记录与当前资料同事务保存，刷新和重启保留；删除案例时移除其修订记录，整体替换资料时替换整套修订记录，不保留隐藏回收站。
- 原出处表示来源沿革，修改内容明确标记为网页修订，不能把旧 CSV 行号冒充修订后内容的逐字证明。回答来源展示相同边界；修订时间与技术摘要不作为调查证据输入模型。

### 5. 时点、快照与并发

- 编辑页展示整份资料的完整可用日期及依据。普通编辑默认沿用；需要改变时与保存一并提交，并确认整份资料在新日期前已结案且内容完整可用。
- 不自动采用保存日或发现日作为结案/完整可用日期；恢复演示时恢复原有日期和说明。继续校验发现时间不晚于登记时点。
- 所有写入采用统一事务边界：核对当前快照、应用操作、校验完整候选集、写入实体/关系/来源/顺序/修订记录/摘要，再读回验证。任一步失败全部回滚。
- 前端提交预期快照 ID；过期编辑、删除、CSV 替换和演示恢复均拒绝写入，返回 409，保留可保留的输入并提示刷新核对。不做自动合并。
- 成功修改产生新身份；原文件摘要继续表示原文件，当前资料由新快照和内容摘要标识，保留基线来源但不伪装为旧内容。
- 已读入旧快照的回答沿旧内容完成，不被写操作取消；新请求读取新资料。旧回答和下载记录不改写、不自动重跑模型。
- 列表、详情与编辑携带快照身份，发现已变化时明确刷新，不混拼新旧记录。
- 文件实验路线、评估标签与历史结果保持隔离。恢复基线和网页维护均不能意外回落到不匹配的固定快照。

### 6. 删除及空库

- 删除确认展示案例编号、摘要、明细/证据数量及受影响分组，说明不提供回收站。取消不产生任何变化。
- 服务端对删除后的完整候选集执行 validator；非法操作即使绕过页面直接请求也必须拒绝。
- 合法删除同时移除案例子记录、来源映射、入组关系和逐案修订记录，维护顺序与摘要；不改主数据或其他案例。
- CR-38 保持每组至少两个不同案例，案例可不入组。若删除导致组不足两案、悬空或其他规则失败，返回具体原因，不自动解散组、不删其他案例。
- 修改造成同站点组失去共同工序也应阻止，不放宽已有业务规则。
- 允许合法删除最后一案，保留数据集元数据及主数据；并不保证任意有组的数据都能逐案删空。不能为了空库目标绕过分组约束。
- 空库显示新增、导入、恢复演示入口；API 对搜索/回答给出明确空库结果，不构建空索引、不调用模型、不返回无法解释的 500。
- 空库与筛选无结果不同；CSV 本身仍要求至少一案。重启保持零案快照。

## 测试决策

以用户可观察行为为验收对象，复用现有 API/真实 PostgreSQL/浏览器接缝，不为每个内部函数建立镜像测试。

- API：列表筛选和完整详情、输入边界、错误定位、版本冲突、空库响应。
- 真实 PostgreSQL：恢复/保存/删除事务、失败回滚、来源和修订记录一致性、重启保留、跨请求快照一致。
- 浏览器：九案恢复、完整浏览、修改/取消/失败、新增多子记录、展开修订、删除拦截、空库重建；桌面和窄屏截图。
- 离线回答回放：新请求使用新内容、进行中请求保持旧快照、来源定位及网页修订标记，不作回答质量结论。
- 回归：既有 CSV 上传、主数据参考、设置、文件实验入口和原始数据不受破坏。
- 每包执行必要验证并记录证据，最终包补跨包闭环。测试数据库不可用则标明未运行，不能用模拟响应代替真实库证据。
- 本任务不需要付费模型调用、不调 Locked Test、不继承旧指标作为新资料效果。

## 范围之外

主数据编辑、完整分组管理、多数据集切换、统计图表、单元格即时编辑、自动保存、服务端草稿发布、回收站、全文版本对比、回滚、编辑者账号、附件上传、通用数据库管理、检索算法升级、正式质量评测及新的演示脚本。

## 补充说明

最终工作包和依赖已获用户确认，常规实现细节由执行者在现有结构中收敛，无需重开已结束的需求访谈。发现必须修改冻结业务规则、跨仓库或迁移/删除实际用户数据时，遵守仓库对应要求。

本规格覆盖旧升级规范的“两页、只整份替换、不逐案编辑”目标限制，其余领域及评估约定继续有效。01–03 已实现并待真实库验收；已有整案编辑与正式修订，整案新增/删除尚未实现，当前运行行为说明随各包实际落地更新。
